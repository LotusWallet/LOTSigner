## §2 构建过程中的三个障碍（复现者必读）

### 2.1 turbo 无法 spawn 子进程

`npx turbo build --filter=caravan-coordinator` 在首个包 `@caravan/build-plugins` 即失败：

```
unable to spawn child process: 所有的管道范例都在使用中。 (os error 231)
```

**在 Git Bash、PowerShell、以及脱离沙箱的 PowerShell 中均复现**——因此不是 shell 问题、也不是沙箱问题，而是 turbo 2.0.3 在本机 Windows 环境下的 spawn 行为问题。

**绕过方式**：直接按依赖拓扑逐个构建，已验证全部成功：

```
caravan-bitcoin → multisig → bip32 → caravan-psbt → caravan-clients
                → transactions → caravan-wallets → caravan-health  (+ build-plugins)
```

每个包执行 `npx tsup src/index.ts --format cjs,esm --dts`（与官方 `build` 脚本一致）。
随后 `npx vite build` 构建 coordinator 本体（**跳过 `tsc` 类型检查**——目标是取得可运行产物，不是验证 Caravan 的类型正确性；此偏离如实记录）。

### 2.2 esbuild postinstall 的 EBUSY

首轮 `npm install` 在 esbuild 的 `install.js` 校验阶段失败：`spawnSync node.exe EBUSY`。
但 `esbuild.exe --version` **直接执行成功**（v0.25.3，平台二进制 `@esbuild/win32-x64` 已就位）。
处理：改 `npm install --ignore-scripts`（install.js 仅做版本校验，跳过无功能损失）。

### 2.3 Git Bash 的 PATH 盘符冲突

`export PATH="C:/xxx:$PATH"` 不生效——盘符冒号与 PATH 分隔符 `:` 冲突。
必须用 `/c/xxx`。曾导致一次 4 分钟的无效安装（node 版本实际未切换）。

## §4 关键动作实测：免配置导入 PSBT（差异项①的探测）

**操作**：直接进入 `/#/script`，**不做任何钱包配置**，上传 `S1.psbt`。

### 4.1 第一次：固件带 CRLF → 报错（已证实为固件格式问题，非 Caravan 能力问题）

```
Error loading PSBT: Input cannot be bufferized.
```

**根因（已查证）**：

1. Caravan 用 `FileReader.readAsText()` 读取文件，**不做 trim**（`ScriptEntry.jsx:294–321`）
2. 内容交给 `bufferize()`（`packages/caravan-psbt/src/functions.ts`），该函数只接受**合法 hex 或合法 base64 字符串**
3. 我最初生成的固件末尾带 `\r\n`，`validBase64()` 判定失败 → 抛错

**这是一个差点造成方向性误判的陷阱**：若直接采信该报错，会得出"Caravan 无法导入 PSBT"的结论，
而真实原因是固件文件的换行。已修正生成器为**无换行的纯 base64 字节写入**，并在代码注释中固化该教训。

> 附带的事实：Caravan 对**带换行的 base64 文件不健壮**——真实场景中用户用文本编辑器保存的
> `.psbt` 常有尾随换行。这是健壮性缺陷，但**不是能力缺失**，判定差异项①时不得计入。

### 4.2 第二次：固件无 CRLF → 解析成功，但后续报错

```
Cannot read properties of undefined (reading 'toString')
```

**根因（已查证）**：`ScriptEntry.jsx:301–303`

```js
if (psbt?.data?.inputs.length > 0) {
  const redeemScriptHex = psbt.data.inputs[0].redeemScript.toString("hex");
```

Caravan 读取的是 **PSBT_IN_REDEEM_SCRIPT（keytype 0x04）**，
而我的 S1 固件是 **P2WSH 多签**，携带的是 **PSBT_IN_WITNESS_SCRIPT（keytype 0x05）**，无 redeemScript 字段 → `undefined.toString()` 崩溃。

**固件 input 字段实测构成**（自解析器 + bip174 双重确认）：

| 样本 | input[0] 字段 |
|---|---|
| S1 | WITNESS_UTXO / SIGHASH_TYPE / **WITNESS_SCRIPT** / BIP32_DERIVATION |
| S2a | SIGHASH_TYPE / **WITNESS_SCRIPT** / BIP32_DERIVATION |
| S2b | 同上 + PROPRIETARY(0x0f) |
| S3 | 同上 + PARTIAL_SIG |

**待验证的问题**（下一阶段执行）：
Caravan 的该导入路径是否**只支持含 redeemScript 的 P2SH 系 PSBT**，
而对现代主流的 P2WSH PSBT 直接崩溃？
→ 需构造一个含 `PSBT_IN_REDEEM_SCRIPT` 的对照样本（S1-P2SH）实测。
**在得到该对照结果前，差异项①不作任何判定。**

## §5 本阶段的两个方法论收获

### 5.1 「固件缺陷被误判为竞品差异」确有现实风险

本阶段实际遇到了两次：33 字节 txid（上一阶段）、CRLF 换行（本阶段）。
二者都会让任何标准解析器/导入器失败，而**导入失败正好落在差异项①（阻断项）上**。
若不加甄别，会把自己的固件缺陷写成"Caravan 做不到"的差异化证据 —— 这在 G3 里是方向性错误。

已固化的防线：
- 固件生成器加 `assert len(hex) == 64`
- 固件写为无换行纯 base64
- **每次报错先归因到"我的固件"还是"被测对象"，再决定是否记录为差异事实**

### 5.2 界面探测本身就能证伪预设

预注册阶段的预设是"Caravan 可能没有免配置导入入口"。
实测发现 **Script Explorer 存在 `Import PSBT` 入口，且不需要预先配置钱包**。
→ 差异项①的判定方向已经与预设不同，必须以实测为准，不得沿用预设。
