## §1 目的与判定语义

**G3 验证的是**：Caravan 是否覆盖了 Lotus Signer 的差异化主张。

| 结果 | 含义 | 后续 |
|---|---|---|
| **通过** | 差异项达到门槛 → 差异化成立 | 进入 G1 |
| **有条件通过** | 仅质量项达标 → 护城河强度低一个量级 | 需重新评估投入产出 |
| **不通过** | Caravan 已覆盖核心主张 | **一级否决，方向重估** |

⚠️ **结论边界**：本结论**仅适用于浏览器形态**。
**不得外推为"受托审阅场景无竞品"**——Sparrow（桌面）同样能审阅 PSBT。此边界必须写进最终报告。

## §3 五项差异任务与分类 —— 🔒 冻结项

| # | 差异项 | 分类 | 判定标准（满足任一即计该项存在差异） |
|---|---|---|---|
| ① | **免配置导入 PSBT** | **工作流阻断** | 导入 PSBT 前必须完成钱包配置 / 导入 descriptor / 提供扩展公钥，**无法直接审阅他人递来的 PSBT** |
| ② | 信息完整度 | 质量差距 | 展示字段不足以判断"这笔交易是否符合预期"（例如缺找零识别、缺手续费、缺输入来源、缺锁定时间） |
| ③ | **导出部分签名** | **工作流阻断** | 签名后**无法导出可供发起方继续收集其余签名的 PSBT**（或导出格式不可被第三方工具消费） |
| ④ | 离线可用性 | 质量差距 | 审阅流程依赖网络请求（区块浏览器 API、UTXO 查询等） |
| ⑤ | xpub 隐私 | 质量差距 | 为完成审阅必须向工具提供扩展公钥（xpub），从而暴露地址全集 |

### 差异簇规则 —— 双向约束（2026-10-11 强化，采纳顾问 A）

同一底层缺失导致的多个表现，合并为一个差异簇，**只计 1 项**。

但这条规则是**双向**的，两个方向都禁止：

| 方向 | 禁止行为 | 举证要求 |
|---|---|---|
| **不得随意合并**（少算） | 仅因两项"看起来相关"或"都涉及 PSBT"就并为一簇 | 合并须**举证两者源自同一底层能力缺失** |
| **不得拆分凑数**（多算） | 把一个底层缺陷的多个表现包装成独立差异项以凑足门槛 | 同一底层的不同表现只计 1 项 |

> 顾问 A 原话：*"① 与③ 虽然都是阻断项，却不能仅因它们都涉及 PSBT 就合并为同一差异簇；
> 反过来，也不能把一个底层缺陷包装成两个独立差异来凑足门槛。"*

**已知候选簇清单（实测中须逐条显式举证或排除，禁止默认）：**

| 候选 | 默认关系 | 举证方向 |
|---|---|---|
| **① 与 ⑤** | 潜在同簇 | 若"必须配置钱包"的**唯一原因**是需要 xpub 才能解析 → 同源，**只计 1 项** |
| **① 与 ③** | **默认不同簇** | 不得仅因两者都涉及 PSBT 而合并；须证明同一底层缺失才可合并 |

**每项簇判断都必须在报告中写明依据**（"是/否同簇 + 底层原因 + 证据等级"）。

## §4 判定规则 —— 🔒 冻结项

### 4.1 门槛

```
通过         = (阻断项 ≥ 1) 且 (合计差异项 ≥ 2)
有条件通过   = (阻断项 = 0) 且 (合计差异项 ≥ 2)     ← 仅质量项凑数
不通过       = 合计差异项 ≤ 1
```

> 设计依据（V4）：**阻断项代表"不通则工作流走死"，质量项只代表"体验更好"**。
> 两者不等价，不能无差别计数——否则会把"不如人但能干活"包装成"别人做不到"。

### 4.2 证据等级

| 等级 | 定义 | 可否计入 |
|---|---|---|
| **A** | 用户实测中真实遇到阻塞，有操作记录与原始输出 | ✅ 可计入 |
| **B** | 有可交付的任务证明或替代方案证明（如"必须执行 X 步骤才能继续"） | ✅ 可计入 |
| **C** | 推测、文档推断、"应该如此" | ❌ **不计入** |

**每项差异必须标注证据等级并附原始输出。C 级单独列于"未采信"区，不得混入判定表。**

### 4.3 双维度记录要求

每项须同时记录：

- **(a)** Caravan 是否满足该项能力
- **(b)** 该缺失**对目标用户是否构成真实阻塞**

> 只记 (a) 会得出"Caravan 做不到、但用户根本不在乎"的**伪差异化**。这是 V3 §G3 加严的核心原因。

目标用户定义（V3 终裁）：熟悉自托管与多签、能判断交易是否符合预期、**但不愿仅凭原始 PSBT 或单一钱包界面作签名决定**的技术型用户。

### 4.4 三字段独立记录 —— 🔒 冻结项（采纳顾问 A 第五轮）

> **核心原则：不能把「差异项成立」与「真实阻塞成立」混为一谈。**

每项差异必须拆成**三个独立字段**记录，缺一不可：

| # | 字段 | 要求 |
|---|---|---|
| 1 | **功能事实** | 目标版本是否支持该操作，**必须附原始操作记录或输出** |
| 2 | **用户影响** | 该事实是否**阻断任务**，或造成**可证明的**显著额外步骤 / 隐私代价 / 信息缺口 |
| 3 | **证据等级与差异簇** | 归为 A/B/C 并记录**底层原因**；C 级不得独立计入，重复表现只计一次 |

**为什么必须拆开**：若只有一个"是否成立"的布尔字段，
"Caravan 做不到"会被默认等同于"用户被卡住"——这正是 V3 加严 G3 时要防的**伪差异化**
（"Caravan 做不到、但用户根本不在乎"）。三字段强制两者分开计价。

**判定组合对照表**：

| 功能事实 | 用户影响 | 结论 |
|---|---|---|
| 不支持 | 阻断任务 | ✅ 计入（真实差异） |
| 不支持 | 有替代路径、仅多几步 | ⚠️ 计入但须写明替代路径与实际代价 |
| 不支持 | 用户不在乎 | ❌ **不计入**，列入"未采信"区 |
| 支持但体验差 | 体验较差 | ❌ 不计为差异，仅记入观察 |
| 文档未提及 | — | ❌ C 级，**不计入**；不得以文档缺失代替实测 |

### 4.5 ④ 的升级路径 —— 🔒 冻结项

若实测发现**特定网络依赖导致核心任务完全无法完成**（即④实质为阻断项），
处理方式：**先按原分类（质量项）记录事实，再走预注册变更程序**。

**严禁在报告中私自改判分类。** 变更须记为「闸门修订」并取得三方确认。

> 这条为的是防止"边跑边改"——分类若可事后调整，预注册即形同虚设。

## §5 必拒错误清单 —— 🔒 冻结项

出现以下任一情况，该项判定（乃至整个 G3）**直接作废**：

| # | 必拒错误 |
|---|---|
| E1 | 测试对象版本未锁定，或混用了多个版本的观察结果 |
| E2 | 以 C 级推测充当差异证据 |
| E3 | 同一差异簇被重复计数，**或**仅因两项同类（如都涉及 PSBT）就合并为同簇而无同源举证 |
| E4 | 只记录 (a) 未记录 (b)（缺用户阻塞性维度） |
| E5 | 结论外推到浏览器形态之外 |
| E6 | 无原始输出佐证（截图/日志/命令行输出缺一不可） |
| E7 | 测试后修改了本预注册文件的 §2–§5 而未经三方确认 |
| **E8** | **三字段缺一**：未分别记录「功能事实 / 用户影响 / 证据等级与差异簇」任一项 |
| **E9** | **私自改判某项分类**（尤其是把④离线可用性由质量项升为阻断项），未走闸门修订程序 |
| **E10** | 以"文档未提及"代替实测来主张差异成立 |
